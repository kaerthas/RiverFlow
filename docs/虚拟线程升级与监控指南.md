# RiverFlow 虚拟线程升级与监控指南

## 一、前置条件

虚拟线程（Virtual Threads）在 **JDK 21** 正式发布。升级前请确认：

1. 本地/测试/生产环境已安装 **JDK 21**（LTS）。
2. Maven 构建使用 JDK 21：
   ```bash
   java -version
   mvn -version
   ```
3. 重新导入 Maven 项目，让 IDE 识别新的 SDK。

## 二、已完成的改造点

| 模块 | 改造内容 | 文件 |
|---|---|---|
| 构建 | JDK 17 → 21 | `pom.xml`、`river-minio/pom.xml` |
| Web 入口 | 开启 Spring Boot 全局虚拟线程 | `riverflow-admin/src/main/resources/application.yml` |
| 流程调度 | `flowExecutor` 改为带信号量限流的虚拟线程执行器 | `FlowExecutorConfig.java` |
| 异步日志 | `AsyncLogService` 改为带信号量限流的虚拟线程执行器 | `AsyncLogService.java` |
| 并发保护 | 新增 `SemaphoreExecutorService` 包装器 | `SemaphoreExecutorService.java` |

## 三、关键配置说明

```yaml
spring:
  threads:
    virtual:
      enabled: true

riverflow:
  virtual-thread:
    flow-executor-max-concurrency: 30   # 流程任务最大并发
    log-executor-max-concurrency: 10    # 异步日志最大并发
```

### 3.1 `spring.threads.virtual.enabled=true`

Spring Boot 3.2+ 开启后，以下组件会自动使用虚拟线程：
- **Undertow** Web 请求处理线程
- **Spring `@Async`** 默认执行器 `applicationTaskExecutor`
- **Spring `TaskScheduler`** 定时任务调度线程
- 其他 Spring 管理的 `Executor` Bean（除非显式指定了平台线程池）

### 3.2 信号量限流参数

虚拟线程本身没有并发上限，但外部资源（数据库连接池、HTTP 连接池）有上限。信号量用于保护这些资源：

- `flow-executor-max-concurrency`：建议不超过数据库连接池 `max-active` 的 1~2 倍。
- `log-executor-max-concurrency`：日志写入主要为 DB 操作，建议 5~20。

> 当前配置：`druid.max-active=20`，`httpclient.max-total=200`。
> 流程节点可能同时访问 DB 和 HTTP，因此 `flow-executor-max-concurrency=30` 是较为保守的初始值，需根据压测调整。

## 四、上线前验证清单

1. **编译通过**
   ```bash
   mvn clean compile -DskipTests
   ```

2. **启动成功**
   ```bash
   mvn spring-boot:run -pl riverflow-admin
   ```
   观察日志中是否出现：
   ```
   初始化流程任务虚拟线程执行器，最大并发数: 30
   异步日志服务初始化完成，虚拟线程执行器最大并发数: 10
   ```

3. **功能回归**
   - 同步流程执行 `/open/flow/executeSync`
   - 异步流程调度（等待 `FlowScheduler` 触发）
   - 插件上传/下载
   - 异步日志保存

4. **虚拟线程是否生效**
   ```bash
   jcmd <pid> VM.version
   jcmd <pid> Thread.dump
   ```
   查看线程名是否包含 `VirtualThread` 或 `undertow-worker-` 前缀（不同版本输出可能不同）。

## 五、监控与调优

### 5.1 关键指标

| 指标 | 监控方式 | 健康阈值 |
|---|---|---|
| 平台线程数 | `ThreadMXBean` / `jstack` | 保持低位，虚拟线程数大但平台线程数小 |
| 虚拟线程数量 | JFR `jdk.VirtualThreadStart` / `jdk.VirtualThreadEnd` | 随流量波动，避免持续暴涨 |
| Carrier Thread Pinning | JFR `jdk.VirtualThreadPinned` | 极少或没有 |
| DB 连接池使用率 | Druid 监控 `/druid/index.html` | < 80% |
| HTTP 连接池使用率 | 自定义指标或日志 | < 80% |
| 任务队列等待 | `SemaphoreExecutorService` 信号量可用许可 | 接近 0 说明并发已打满 |

### 5.2 使用 JFR 监控 Virtual Thread Pinning

```bash
jcmd <pid> JFR.start name=vt settings=profile filename=/tmp/vt.jfr
# 压测一段时间后
jcmd <pid> JFR.stop name=vt
```

使用 JDK Mission Control 打开 `vt.jfr`，查看 `Java Application` → `Virtual Threads` 事件：
- **Pinned**：虚拟线程被钉在平台线程上，通常由 `synchronized` 块或本地代码引起。
- **Started / Ended**：虚拟线程创建/销毁速率。

### 5.3 调优建议

1. **出现 DB 连接池耗尽**
   - 降低 `flow-executor-max-concurrency`。
   - 增加 Druid `max-active`（需评估 MySQL 端连接上限）。

2. **出现 HTTP 连接池耗尽**
   - 降低 `flow-executor-max-concurrency`。
   - 增加 `httpclient.max-total` 和 `max-per-route`。

3. **Carrier Thread 被大量 Pin**
   - 检查堆栈，定位 `synchronized` 块。
   - 将 `synchronized` 替换为 `ReentrantLock`。
   - 当前项目外部库（Apache HttpClient 4.x、Druid）内部可能有少量 pinning，通常影响可控。

4. **内存占用上升**
   - 检查 `ThreadLocal` 使用，特别是 `DynamicDataSourceContextHolder`、`SecurityContextHolder`。
   - 高并发下每个虚拟线程一份 ThreadLocal 副本，需确保不会持有大对象。

## 六、回退方案

如果上线后发现问题，可快速回退：

1. **关闭全局虚拟线程**
   ```yaml
   spring:
     threads:
       virtual:
         enabled: false
   ```

2. **恢复流程执行器为平台线程池**
   将 `FlowExecutorConfig.flowExecutor()` 改回原来的 `ThreadPoolExecutor` 实现。

3. **恢复异步日志执行器**
   将 `AsyncLogService.init()` 改回 `Executors.newFixedThreadPool(2, ...)`。

## 七、后续可优化项

| 优先级 | 事项 | 说明 |
|---|---|---|
| P1 | 分布式调度锁 | `FlowScheduler` 多节点会重复扫描，建议引入 ShedLock 或 Redisson 看门狗 |
| P2 | MinIO 插件虚拟线程化 | 插件执行层可统一包装到虚拟线程执行器 |
| P2 | Groovy 脚本沙箱 | 脚本执行使用虚拟线程，避免 `Thread.sleep` 或 HTTP 阻塞平台线程 |
| P3 | 虚拟线程指标暴露 | 通过 Micrometer/Actuator 暴露虚拟线程数量、pinning 次数等指标 |

## 八、一句话总结

> 本项目已具备虚拟线程运行条件：JDK 21 + Spring Boot 3.2 + Undertow + 信号量限流。上线后重点关注 DB/HTTP 连接池水位和 JFR pinning 事件。
